# Scaleway Terraform – Correspondence internal PoC

A repository-ready starting implementation for a Digdir-owned internal PoC.
Reusable **Scaleway** modules live under
`cloud-providers/scaleway/terraform/modules`; the **Correspondence** composition
lives under `environments/internal-poc/correspondence/scaleway/terraform`.
Code and repository documentation are in English. Start with [START_HER_NO.md](START_HER_NO.md).

This package provisions infrastructure and offers separate HTTP/runtime and
private-service connectivity checks. Running the unchanged Azure Correspondence
image is **not** a complete application port. See [docs/APPLICATION_PORTING.md](docs/APPLICATION_PORTING.md).

## Included modules

| Module | Purpose | Default PoC use |
|---|---|---|
| `private-network` | Dedicated VPC, Private Network and IPAM | Enabled |
| `postgresql` | Private Managed PostgreSQL and application database | Enabled |
| `redis` | Single private TLS-enabled Managed Redis node | Enabled |
| `object-storage` | Private, versioned S3 bucket | Attachments |
| `secret-manager` | Secrets and version payloads | DB/Redis strings and optional app secrets |
| `container-registry` | Private Scaleway image namespace | Enabled; images pushed separately |
| `serverless-container` | Private-network-attached HTTP workload | Nginx first, then probe or ported API |
| `serverless-job` | Job definition with Secret Manager references | Standalone; no database migration wiring |

Scaleway Serverless Jobs currently cannot attach to a Private Network. Therefore
they cannot run migrations against this private PostgreSQL instance. The dedicated
job module does not invent network arguments and is not instantiated by this root.
Use a VPC-connected self-hosted runner or another workload with private access.

## Import into the existing portability repository

Extract this ZIP, then copy the **contents** of the top-level folder into the repo
root. Preserve existing files and merge any existing `.gitignore` or workflows.
Include `.github`, `.gitignore`, `.terraform-version` and the two root
`.terraform.lock.hcl` files. Do not put the whole package under one extra directory:
module paths traverse exactly five parent directories from the environment root.
No Correspondence application source has been copied into the portability repository.

## Versions and verification

- Workflow CLI: Terraform **1.13.5**; configuration supports >=1.13 and <2.
- Provider: **scaleway/scaleway 2.86.0**, pinned in roots/modules and lock files.
- Dependency checksums: generated by `terraform init`; commit lock files.
- Local verification results and limits: [docs/VALIDATION.md](docs/VALIDATION.md).
- CI runs `fmt`, initialization/validation for all eight modules and both roots,
  mocked plan tests, CI helper tests, probe cleanup/error-disclosure tests and syntax checks without cloud credentials.

## 1. Prepare a Digdir project and IAM credentials

Use a Digdir-owned organization/project, with agreed billing, project owner and
PoC cleanup responsibility. Use an IAM application API key for automation, not a
personal API key. The project needs access to VPC/Private Networks, Managed
PostgreSQL, Managed Redis, Object Storage, Secret Manager, Container Registry and
Serverless Containers. Check organization quotas and regional product availability.

Keep API keys outside Terraform inputs. Provider authentication reads
`SCW_ACCESS_KEY`, `SCW_SECRET_KEY`, `SCW_DEFAULT_ORGANIZATION_ID` and
`SCW_DEFAULT_PROJECT_ID` from environment variables. The S3 backend uses separate
AWS-compatible environment variable names; that does not create an AWS dependency.
Prefer separate state-bucket and runtime S3 keys scoped to their required resources.

## 2. Bootstrap remote state once

Use `cloud-providers/scaleway/terraform/bootstrap/state` locally as documented
there. The bootstrap bucket is versioned and has `prevent_destroy = true`.
Keep its local state securely. Do not put state in Git or GitHub artifacts.
If the state bucket already exists, import it or use it after checking access and versioning.

The application backend uses S3 conditional writes via `use_lockfile = true`.
Bucket IAM must allow state Get/Put/List and lockfile Get/Put/Delete. A separate
state key can be supplied with the optional state credentials below.

## 3. Configure GitHub

Create the GitHub environment **`scaleway-internal-poc`**. Restrict its deployment
branches to your default branch and configure required reviewers if your team's
policy calls for that. Add the following environment secrets/variables (repository
scope is also supported).

| GitHub setting | Kind | Required / purpose |
|---|---|---|
| `SCW_ACCESS_KEY` | Secret | IAM application access key |
| `SCW_SECRET_KEY` | Secret | IAM application secret key |
| `SCW_ORGANIZATION_ID` | Variable | Digdir organization UUID |
| `SCW_PROJECT_ID` | Variable | Digdir project UUID |
| `SCW_STATE_BUCKET` | Variable | Existing bootstrap bucket |
| `SCW_STATE_REGION` | Variable | Optional; default `fr-par`, independent of compute region |
| `POC_DATABASE_PASSWORD` | Secret | 16-128 characters including upper/lowercase, digit and underscore/hyphen; stable until deliberate rotation |
| `POC_REDIS_PASSWORD` | Secret | Same allowed password format and complexity |
| `SCW_TFVARS_JSON` | Variable | Non-secret overrides; default `{}` |
| `SCW_STATE_ACCESS_KEY` | Secret | Optional separate backend key; falls back to SCW_ACCESS_KEY |
| `SCW_STATE_SECRET_KEY` | Secret | Optional separate backend key; falls back to SCW_SECRET_KEY |
| `SCW_REGISTRY_ENDPOINT` | Variable | Required only for building probe; set from Terraform output |
| `POC_S3_ACCESS_KEY` | Secret | Required for connectivity mode; separate runtime bucket access |
| `POC_S3_SECRET_KEY` | Secret | Runtime S3 key with Put/Get/DeleteObject and DeleteObjectVersion |
| `POC_APPLICATION_SECRETS_JSON` | Secret | Optional JSON map of app integration secrets |

Example `SCW_TFVARS_JSON` for the first run:

```json
{
  "region": "fr-par",
  "zone": "fr-par-1",
  "name_prefix": "altinn-corr-internal-poc",
  "redis_version": "REPLACE-WITH-AVAILABLE-PATCHED-VERSION",
  "container_mode": "smoke",
  "container_privacy": "private",
  "min_scale": 0
}
```

`redis_version` is required rather than hardcoding an old engine patch. List
available versions with `scw redis version list zone=fr-par-1` (or the Scaleway
console) and replace the placeholder with a currently supported patched version.
The mock suite uses 8.4.0 as dummy configuration; it is not an availability claim.

The helper rejects passwords/runtime credentials in `SCW_TFVARS_JSON`. Provide
extra app secret names as a non-secret `application_secret_names` list there;
the list must exactly match keys in `POC_APPLICATION_SECRETS_JSON`. Names
`database-connection-string` and `redis-connection-string` are reserved.

## 4. Run GitHub Actions

Commit the files to your existing repo, using a normal branch/PR. If the repo's
primary branch is not `main`, adjust `push.branches` in the Terraform workflow.
Pull requests and pushes only run local CI checks; they never deploy or read cloud secrets.

From Actions, run **Scaleway Terraform** on the default branch:

1. Choose **plan** and inspect its log and estimated resource changes.
2. Choose **apply** to generate a fresh plan and apply that exact plan in one run.
3. Inspect non-secret outputs for URL, database/cache endpoints and registry.

The apply run replans; the earlier plan is a review aid, not a saved approval
artifact. Deployments use one concurrency group and remote state locking.
The saved plan can contain secrets, stays on the runner, and is never uploaded
as a GitHub artifact. The bootstrap root is never deployed/destroyed by this workflow.

## 5. Test the first container

Private invocation uses the Scaleway API key header. This is independent from
attaching the container to the Private Network. On a trusted local shell, with
`SCW_SECRET_KEY` already loaded from your secret store:

```bash
export CONTAINER_ENDPOINT="https://REPLACE-WITH-CONTAINER-ENDPOINT"
curl --fail --retry 5 --retry-delay 5 \
  -H "X-Auth-Token: $SCW_SECRET_KEY" "$CONTAINER_ENDPOINT/"
```

Successful nginx output confirms HTTP container deployment only. It does **not**
confirm database/cache/object-store access. A Docker Hub tag is used for this first
run; copy it to the Scaleway registry or pin its digest for repeatable future runs
and to reduce dependence on external registry rate limits.

## 6. Run private-service connectivity checks

1. Set `SCW_REGISTRY_ENDPOINT` to the `registry_endpoint` output (no scheme).
2. Run **Scaleway Build Connectivity Probe**. It builds linux/amd64 and pushes
   `connectivity:<commit-sha>` to the existing private registry.
3. Provision a separate runtime IAM API key with access to the attachment bucket,
   including deleting a specific object version. Set `POC_S3_ACCESS_KEY` and
   `POC_S3_SECRET_KEY`; the probe does not receive the infrastructure automation key.
4. Update `SCW_TFVARS_JSON` with `container_mode = "connectivity"` and the image
   printed by the build workflow. Run plan and apply again.
5. Call `$CONTAINER_ENDPOINT/checks` with the authentication header.

Expected result:

```json
{"postgresql":{"status":"ok"},"redis":{"status":"ok"},"object_storage":{"status":"ok"}}
```

The probe runs PostgreSQL `SELECT 1`, Redis PING/set/get/delete, and S3
put/get/delete of a unique temporary object. It deletes the precise object
version to avoid leaving test versions/delete markers behind. `/` and `/health`
only check process liveness so data-service failures do not block deployment.
Failed checks return HTTP 503 and an exception **type**, never exception messages
or credentials. PostgreSQL verifies the CA chain using `verify-ca`; this does
not claim hostname verification. Redis requires CA and hostname verification.
If the Redis certificate does not cover its private IP, verify its certificate
names/DNS and override `REDIS_HOST` in `application_environment` to the matching,
privately resolvable hostname. Do not turn off certificate validation.

## 7. Port the actual application

Only after the probe passes, prepare an adapted Correspondence image. Set
`container_mode = "correspondence"`, its image digest, `min_scale >= 1`, approved
integration configuration and secrets. The root uses the source image's real
port **2525**, process liveness `/healthz`, a proposed `ScalewayPoc` environment, password-based
PostgreSQL authentication and TLS Redis. The new environment configuration must
be added by the application team; it does not already exist in the uploaded code.

PostgreSQL's connection string points to `/app/certs/postgresql-ca.pem`: export
`postgresql_ca_pem` and install/mount the CA in the adapted image. Redis needs the
exported CA and a valid TLS identity integrated with the .NET client. Secret
Manager payloads alone do not replace Azure Key Vault API calls. S3 environment
keys under `Portability__` are an explicit **proposed adapter contract**, not
existing Correspondence options. See the porting checklist for details.

## Cleanup and cost

PostgreSQL, Redis, database storage/backups and retained S3 versions continue to
cost money even when the HTTP container has zero replicas. Set a PoC budget,
owner and end date; get current prices/quotas in the Digdir project before apply.
No guessed price or production capacity estimate is encoded here.

Run **destroy** with confirmation equal to the configured `name_prefix`. It
removes the environment's Terraform-managed resources, including DB contents.
By default a non-empty attachment bucket blocks deletion; inspect/export and
empty all relevant versions first. Set `force_destroy_attachments = true` only
if the owner deliberately wants permanent deletion. Terraform destroy is not
transactional: some resources can already be deleted if bucket deletion fails.
The bootstrap state bucket remains; keep remote state and credentials until
cleanup has completed. Registry images and unmanaged test resources may need
separate cleanup according to their product retention behavior.
